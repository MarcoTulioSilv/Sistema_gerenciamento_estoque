Fase 1 — Fundação
Sprint 0 — Setup e infraestrutura Ambiente, banco de dados, estrutura de projeto e CI
Semanas 1–2
Pré-requisito: servidor MySQL disponível
Itens do backlog
Criar estrutura de pacotes Python (MOD-01 a MOD-06, gui, main.py)
Configurar MySQL Server 8.x e criar schema sce_db
Escrever DDL completo (9 tabelas, índices, constraints)
Configurar SQLAlchemy 2.0 com pool de conexões
Configurar PyInstaller + Inno Setup (build de teste)
Configurar ambiente de desenvolvimento (venv, requirements.txt)
Estrutura base CustomTkinter (janela principal, tema, menu lateral)
Critérios de aceitação
Schema MySQL criado e validado via Workbench
SQLAlchemy conecta ao banco e executa query de teste
Janela principal abre sem erros no Windows 10
Build .exe gerado e executável em máquina limpa
Estrutura de pacotes reflete os 6 módulos do DAS
Entrega ao final da sprint
Ambiente configurado Banco criado (DDL) Janela principal vazia Build .exe funcional
Dependência externa:Servidor MySQL deve estar instalado e acessível antes do início desta sprint. Responsabilidade do TI do cliente.
Fase 2 — Núcleo operacional
Sprint 1 — MOD-01 Autenticação e acesso Login, sessão, perfis e controle de permissões
Semanas 3–4
Depende: Sprint 0 concluída
Itens do backlog
Tela T-01 — Login (wireframe + implementação)
AuthService: validação de credenciais com bcrypt
SessionManager: controle de sessão ativa e expiração 30min
PermissionGuard: controle de acesso por perfil por tela
Tela T-02 — Tela inicial com menu lateral por perfil
Tela T-21 — Troca de senha
UsuarioRepository: CRUD básico no MOD-06
Seed: criar usuário TI padrão no banco
Critérios de aceitação
Login com credenciais válidas abre tela inicial com menu correto por perfil
Login com credenciais inválidas exibe erro sem revelar qual campo está errado
Sessão expira após 30 min de inatividade e retorna ao login
Técnico não visualiza itens de menu restritos à Gestora ou TI
Senha armazenada como hash bcrypt — nunca em texto plano
Troca de senha exige senha atual antes de aceitar nova
Entrega ao final da sprint
T-01 Login funcional T-02 Tela inicial T-21 Troca de senha Controle de perfis
Ao final desta sprint o sistema já pode ser instalado nas estações e os usuários conseguem se autenticar. Primeiro entregável demonstrável ao cliente.
Sprint 2 — MOD-02 Estoque parte A Cadastros: produto, fornecedor, lote e entrada manual
Semanas 5–6
Depende: Sprint 1 concluída
Itens do backlog
Tela T-03 — Listagem de produtos com filtros e badges de situação
Tela T-04 — Listagem de fornecedores
Tela T-05 — Cadastro/edição de produto (todos os campos RF-01)
Tela T-06 — Cadastro de fornecedor
Tela T-07 — Registro de entrada manual com leitor de barras
ProdutoRepository, FornecedorRepository, LoteRepository
EstoqueService: cadastrarProduto, cadastrarFornecedor, registrarEntradaManual
Validação número NF obrigatório (RN-07)
Cálculo automático valor_total = qtd × valor_unitario
Critérios de aceitação
Produto cadastrado com todos os campos de RF-01 (nome, EAN, marca, fornecedor, centro_alocação, estoque mínimo)
EAN duplicado é rejeitado com mensagem clara
Leitor de código de barras preenche campo EAN automaticamente (HID USB)
Entrada manual bloqueada sem número de NF (RN-07)
Valor total calculado automaticamente ao informar qtd e valor unitário
Lote criado vinculado ao produto correto com data de vencimento válida
Entrega ao final da sprint
T-03 Produtos T-04 Fornecedores T-05 Novo produto T-06 Novo fornecedor T-07 Entrada manual
Ao final desta sprint o Técnico consegue cadastrar o estoque completo via entrada manual.
Sprint 3 — MOD-02 Estoque parte B Importação NF-e XML, retirada multi-lote FEFO e dashboard
Semanas 7–8
Depende: Sprint 2 concluída
Itens do backlog
Tela T-08 — Importação NF-e XML (preview + confirmação)
NFeParser: leitura XML SEFAZ 4.0, validação schema XSD
Atomicidade da importação (RN-06): tudo ou nada
Tela T-09 — Retirada multi-lote com exibição do plano FEFO
FEFOSelector: algoritmo de distribuição multi-lote (RN-08)
Bloqueio RF-09: estoque total insuficiente
Tela T-10 — Posição do estoque com filtros
Tela T-22 — Dashboard de monitoramento com auto-refresh
Marcação de lote esgotado (saldo = 0 após retirada)
Critérios de aceitação
XML NF-e válido importa todos os itens ou nenhum (atomicidade)
EAN não cadastrado gera aviso e permite cadastro antes de continuar
Retirada distribui automaticamente entre lotes FEFO quando necessário
Plano de consumo exibido antes da confirmação (lotes afetados + qtd + saldo restante)
Retirada maior que estoque total é bloqueada com mensagem de qtd máxima
Dashboard T-22 atualiza automaticamente a cada 30 segundos
Lote com saldo zero é marcado como esgotado após retirada
Entrega ao final da sprint
T-08 NF-e XML T-09 Retirada FEFO T-10 Consulta T-22 Dashboard
Sprint mais complexa do projeto. MOD-02 completamente funcional ao final. Marco importante para demonstração ao cliente.
Sprint 4 — MOD-03 Relatórios Geração XLSX, envio por e-mail sob demanda e agendamento
Semanas 9–10
Depende: Sprint 3 concluída, conta Gmail configurada
Itens do backlog
Tela T-11 — Central de relatórios (4 tipos sob demanda)
XlsxBuilder: geração XLSX com formatação condicional (lotes vencidos em vermelho)
RelatorioService: movimentação por período, estoque atual, a vencer 30d, lotes vencidos
GmailClient (MOD-04): envio SMTP com App Password criptografado (Fernet)
Tela T-12 — Configuração de agendamento por tipo de relatório
Tela T-13 — Configuração de estoque mínimo por produto
Tela T-14 — Consulta posição estoque (perfil Gestora)
Log de envio de relatórios
Critérios de aceitação
Relatório de movimentação XLSX gerado corretamente para período definido
Lotes vencidos destacados em vermelho nos relatórios (RF-22)
Relatório enviado por e-mail e recebido na caixa da Gestora
Falha no envio SMTP registrada em log sem cancelar operação
Agendamento salvo e relatório enviado automaticamente no horário configurado
Estoque mínimo alterado pela Gestora reflete imediatamente nas consultas
Entrega ao final da sprint
T-11 Relatórios T-12 Agendamento T-13 Estoque mín. T-14 Consulta XLSX geração Gmail SMTP
Sprint 5 — MOD-04 Notificações e scheduler Alertas automáticos de vencimento, estoque baixo e lotes vencidos
Semanas 11–12
Depende: Sprint 4 concluída (GmailClient pronto)
Itens do backlog
NotificacaoService: lógica de alertas 15d, 7d, 2d e vencidos
Controle de duplicidade via notificacao_log (mesmo lote + marco + dia)
Scheduler APScheduler: job diário de notificações no horário configurado
Alerta imediato de estoque baixo após retirada (evento de MOD-02)
Alerta diário consolidado de lotes vencidos (e-mail + painel T-02)
job_log: registro de cada execução do scheduler (sucesso ou falha)
Painel de alertas na T-02 (lotes vencidos em estoque)
Critérios de aceitação
E-mail de alerta recebido nos marcos de 15, 7 e 2 dias antes do vencimento
Mesmo alerta não enviado duas vezes no mesmo dia para o mesmo lote e marco
Alerta de estoque baixo enviado imediatamente após retirada que atinge o mínimo
Painel de lotes vencidos exibido na tela inicial quando existirem lotes vencidos
Falha no SMTP registrada em job_log sem interromper demais notificações
Scheduler executa no horário configurado independente de interação do usuário
Entrega ao final da sprint
Alertas 15/7/2d Alerta estoque baixo Alerta lotes vencidos Scheduler diário job_log
Ao final desta sprint o sistema está operacional para o cliente — todas as funcionalidades core estão funcionando.
Sprint 6 — MOD-05 Administração Usuários, backup, log de operações e configuração Gmail
Semanas 13–14
Depende: Sprint 1 concluída (pode ser paralelizado)
Itens do backlog
Tela T-15 — Listagem de usuários
Tela T-16 — Cadastro/edição/desativação de usuário
UsuarioService: criar, editar, desativar, redefinir senha
Tela T-17 — Configuração da conta Gmail (SMTP + teste de envio)
ConfigService: armazenamento seguro de App Password com Fernet
Tela T-18 — Backup: disparo manual + configuração de diretório
BackupManager: cópia do banco MySQL via mysqldump
Tela T-19 — Log de operações com filtros por período e usuário
Tela T-20 — Configuração de agendamento (acesso TI)
Critérios de aceitação
TI cria usuário com perfil correto; novo usuário consegue fazer login
Usuário desativado não consegue mais fazer login
App Password armazenado criptografado — nunca visível em texto plano
Teste de envio na T-17 confirma configuração Gmail antes de salvar
Backup gera arquivo .sql datado no diretório configurado
Log exibe todas as operações de entrada, saída e alteração com usuário e data/hora
TI não consegue desativar o único usuário TI ativo (proteção de segurança)
Entrega ao final da sprint
T-15 Usuários T-16 Novo usuário T-17 Gmail T-18 Backup T-19 Log ops T-20 Agendamento
Fase 3 — Finalização
Sprint 7 — Integração e testes Integração end-to-end, testes de todos os fluxos e empacotamento
Semanas 15–16
Depende: Sprints 0–6 concluídas
Itens do backlog
Testes de integração de todos os fluxos críticos (retirada multi-lote, scheduler, importação XML)
Testes de concorrência: Técnico + Gestora acessando simultaneamente
Testes de perfil: verificar que cada ator só acessa o que deve
Testes de borda: estoque zerado, lote expirado, NF duplicada
Ajustes de UX baseados em uso real do sistema montado
Build final .exe + instalador Inno Setup
Documentação de instalação e manual do usuário (TI, Técnico, Gestora)
Script de carga inicial (seed de dados de teste para homologação)
Critérios de aceitação
Todos os 7 critérios de aceitação gerais da ERS v1.5 verificados e documentados
Concorrência: retirada e relatório simultâneos não causam erro ou dado incorreto
Instalador executa sem erros em máquina Windows 10 limpa
Manual de instalação validado pelo TI do cliente
Nenhum bug crítico em aberto
Entrega ao final da sprint
Build .exe final Instalador Inno Setup Relatório de testes Manual do usuário Script de seed

Requisitos funcionais
Cerimônias Scrum por sprint: Planning (início da sprint, 2h) · Daily standup (diário, 15min) · Review com demonstração ao cliente (final, 1h) · Retrospectiva (final, 30min).   Backlog refinement: meio de cada sprint, para preparar itens da próxima.   Definition of Done: código implementado + testes unitários escritos + tela funcional demonstrável + sem regressão nos módulos anteriores.
